# Legacy Adapter Migration

## Current classification

| Component | State | Reason |
| --- | --- | --- |
| `DataSourceManager` | PASSIVE_COMPATIBILITY | Existing consumers still need the facade; ActiveDatasetStore is authoritative for imported metadata. |
| `SpreadsheetWorkspaceManager` | PASSIVE_COMPATIBILITY | Kept for older local workflows; no new source identity or binding is generated by the RC-3 path. |
| `WorkspaceDNAEngine` | MIGRATE_AND_REMOVE | Import decisions and workspace intelligence use the current fingerprint/registry contracts; old UI consumers were removed from the certified journey. |
| `CompensationEngine` | MIGRATE_AND_REMOVE | Commission views use module mappings and seller statements; the legacy engine is not an input to the multi-company path. |
| `EnterpriseDigitalTwinTab` | PASSIVE_COMPATIBILITY | Legacy administration surface remains available, but canonical repository binding is the target for migration. |

## Adapter rules

Compatibility code must not create IDs, persist a second relation, maintain a
source cache, calculate business metrics or emit a parallel event. New code
must import `EnterpriseRepository`, `ActiveSourceSelectionStore`,
`ActiveDatasetStore` and the F8 engines directly.

## Remaining risk

Some legacy screens still read old entity arrays for display and must be
migrated before the adapters can be deleted. They are outside the certified
multi-company resolution path and are not allowed to change canonical
bindings.
